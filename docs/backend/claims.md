# 서버 분리에서 신경 쓴 것

Next.js Route Handler와 raw SQL로도 충분한 규모였지만, 백엔드 학습을 겸해 NestJS와 ORM(Drizzle)으로 서버를 분리했습니다.

## 구성

NestJS 서버(Railway) 하나가 PostgreSQL(Neon)을 사용합니다. 웹과 Android 앱이 같은 서버를 호출하도록 만들었습니다.

DB에 보내는 쿼리는 Drizzle ORM으로 작성하고, 테이블을 만들거나 바꾸는 마이그레이션도 서버의 Drizzle 마이그레이션(drizzle-kit)이 맡습니다.

테이블은 사용자 테이블과 기록 테이블, 둘입니다.

### 사용자 테이블

| 열 | 뜻 |
|---|---|
| id | 사용자 번호 |
| google_sub | Google 계정을 가리키는 값. 게스트면 비어 있습니다 |
| is_guest | 게스트인지 여부 |

이 서비스는 로그인 없이 게스트로 바로 시작할 수 있고, 나중에 Google 계정을 연결할 수 있습니다.

그래서 게스트와 Google 계정을 두 테이블로 나누지 않고 한 테이블에 둡니다. 게스트가 Google 계정을 연결하면 같은 행의 값만 바뀝니다.

| 때 | id | google_sub | is_guest |
|---|---|---|---|
| 게스트로 시작 | 7 | (비어 있음) | true |
| Google 계정을 연결한 뒤 | 7 | google-abc | false |

사용자 번호(7)가 그대로이므로, 게스트 때 남긴 기록을 다른 사용자에게 옮기는 작업이 필요 없습니다.

대신 is_guest와 google_sub가 서로 어긋나면 안 됩니다. 예를 들어 게스트인데 Google 계정 값이 있는 행은 DB가 거절하도록 규칙을 걸어 두었습니다.

### 공부 기록 테이블

| 열 | 뜻 |
|---|---|
| user_id | 누구의 기록인지(사용자 번호) |
| record_date | 날짜 |
| date_type | 평일인지 휴일인지 |
| studied_minutes | 오전·오후·저녁 공부시간(분) |
| fail_tags | 그날 실패한 것들 |

한 사용자의 하루 기록이 한 행입니다. 예를 들어 9월 1일 기록은 이렇게 저장됩니다.

| user_id | record_date | studied_minutes | fail_tags |
|---|---|---|---|
| 7 | 2026-09-01 | [60, 30, 120] | [늦잠, 유튜브] |

공부시간 세 칸과 실패 태그는 행을 따로 나누지 않고, 배열로 같은 행에 둡니다. 화면이 하루 기록을 늘 한꺼번에 읽고 저장하기 때문입니다.

통계(어떤 실패를 반복했는지 등)도 SQL로 집계하지 않습니다. 서버가 그 사용자의 기록을 모두 읽은 뒤, 웹의 예시 화면과 같은 계산 함수로 계산합니다. 한 사람의 기록이라 양이 적기 때문입니다.

## 규칙을 코드가 아니라 DB가 지키게 하기

이 절의 규칙과 처리 방식은 옛 서버(Next.js Route Handler) 때부터 있던 것이고, 서버를 옮기면서도 그대로 유지했습니다.

### 문제

이 서비스는 매일 공부시간과 실패한 것을 한 건의 기록으로 남기고, 달력의 하루 칸에 그 기록을 보여 줍니다. 그래서 한 사용자는 한 날짜에 기록을 하나만 가질 수 있습니다.

이 규칙을 지키는 방법은 두 가지였습니다.

- **코드 방식**: 서버가 그 날짜 기록이 있는지 먼저 SELECT하고, 없을 때만 INSERT합니다
- **DB 방식**: 같은 날짜 기록이 두 번 들어오면 DB가 거절합니다

그 중에, 코드 방식을 수도 코드로 표현한다고 하면 이렇습니다.

```
if(만약 그 사용자의 그 날짜 기록이 이미 있으면)  // SELECT 결과를 기다리는 동안, 다른 요청이 먼저 처리될 수 있다
  "이미 기록이 있는 날짜" 로 거절
```

이 방식은 SELECT와 INSERT가 따로 일어나서, 그 사이에 다른 요청이 끼어들 수 있습니다. 저장 버튼을 빠르게 두 번 누르면 두 요청이 이렇게 겹칩니다.

| 순서 | 요청 A | 요청 B |
|---|---|---|
| 1 | 9월 1일 기록 SELECT → 없음 | |
| 2 | | 9월 1일 기록 SELECT → 없음 (A가 아직 INSERT하기 전) |
| 3 | 9월 1일 기록 INSERT | |
| 4 | | 9월 1일 기록 INSERT → 같은 날 기록이 두 개 |

코드 방식으로 이렇게 끼어드는 것을 막으려면 두 요청이 차례로 확인하게 만드는 장치(예: 잠금)를 따로 둬야 합니다.

### 해결

DB 방식을 선택했습니다. DB는 INSERT하는 순간에 확인까지 함께 하므로, 두 요청이 겹쳐도 늦은 쪽을 거절합니다.

스키마([schema.ts](../../apps/api/src/db/schema.ts))에 같은 사용자·같은 날짜는 하나만 둔다는 제약을 적습니다.

```
기록 테이블 규칙: (사용자, 날짜) 짝은 하나만
```

서버는 미리 SELECT하지 않고 바로 INSERT한 뒤, DB가 이 제약으로 거절하면 409 `DUPLICATE_DATE`로 바꿉니다([study-record.repository.ts](../../apps/api/src/study-record/study-record.repository.ts)).

### 단점

규칙을 바꾸려면 서버 코드만 고쳐서는 안 되고, DB 구조를 바꾸는 작업(마이그레이션)이 함께 필요합니다.

예를 들어 하루에 기록을 여러 개 둘 수 있게 바꾼다고 해 봅시다.

- **코드 방식이었다면**: 규칙이 서버 코드의 조건문에 있으므로, 그 조건문을 지우고 서버를 배포하면 끝납니다
- **DB 방식에서는**: 규칙이 운영 DB의 테이블에 걸려 있어서 아래 일이 더 듭니다
  1. 제약을 지우는 SQL 파일(마이그레이션)을 만듭니다
  2. 그 파일을 운영 DB에 적용합니다
  3. 서버 배포와 순서를 맞춥니다.

그래도 DB 방식을 선택했습니다. 이 규칙은 기록 기능을 처음 만들 때 정한 뒤로 바뀐 적이 없고, 달력이 하루 칸에 기록 하나를 보여 주는 한 바뀔 일도 드뭅니다. 가끔 드는 마이그레이션 비용보다, 같은 날 기록이 두 개 생기는 것을 확실히 막는 쪽이 더 크다고 판단했습니다.

## 서버가 거절한 이유를 code로 전하기

### 문제

웹과 앱은 저장 요청이 거절되면, 무엇이 틀렸는지 사용자에게 알려 줘야 합니다.

그런데 서버가 상태 코드만 응답하면, 화면은 이유를 알 수 없습니다. 같은 400이라도 공부시간이 틀렸는지, 빈 기록인지, 날짜가 틀렸는지 구분되지 않습니다.

그리고 NestJS가 직접 거절한 요청(예: 깨진 JSON 본문)은 영어 문장이 응답되므로, 서버 문장을 그대로 띄우면 영어가 화면에 나옵니다.

### 해결

서버는 모든 거절을 `{code, message}` 한 모양으로 응답합니다. `message`는 사용자에게 보여 줄 한국어 문구이고, 아래 표의 거절이면 화면은 이 문구를 그대로 띄웁니다. 화면이 모르는 code가 오면 서버 문구 대신 "저장하지 못했어요" 안내를 띄우고 오류로 보고합니다. `code`는 화면이 거절 뒤 할 일을 가를 때 씁니다(이미 기록이 있는 날짜면 목록을 다시 받는 식).

| 거절한 이유                      | code | 화면 문구 |
|-----------------------------|---|---|
| 공부시간이 0부터 1440(분) 사이의 정수가 아님 | INVALID_STUDIED_MINUTES | 공부시간은 0~1440 사이의 정수(분)로 적어 주세요 |
| 공부시간도 실패 태그도 없는 빈 기록        | EMPTY_RECORD | 공부시간이나 실패 태그 중 하나는 적어 주세요. 못 했다면 그 이유를 실패 태그로 남겨 보세요 |
| 같은 날짜에 이미 기록이 있음            | DUPLICATE_DATE | 이 날짜엔 이미 기록이 있어요 |
| 본문이 깨진 JSON(NestJS가 거절)     | INVALID_BODY | 요청 형식이 올바르지 않아요 |

이 표의 code 목록과 입력 검증 문구(공부시간·빈 기록)는 웹·앱·서버가 함께 사용하는 패키지(shared)에 둡니다. 중복 날짜, 그리고 NestJS가 직접 거절한 요청처럼 서버만 판단할 수 있는 거절의 문구는 서버에 둡니다.

서버를 분리하면서, 옛 서버에 있던 입력 검증도 새 서버에 복사하지 않고 이 패키지로 옮겼습니다. 새 서버는 그 검증 함수를 그대로 호출하고, 화면의 입력 폼도 같은 글자 수 제한과 같은 문구를 사용합니다. 그래서 폼이 막지 못한 값을 서버가 거절해도, 사용자는 폼에서 보던 것과 같은 문구를 봅니다.

NestJS가 직접 거절한 요청도 서버의 에러 처리 한 곳에서 같은 모양으로 바꿉니다. 영어 문장 대신 정해 둔 code와 문구가 응답됩니다.

### 단점

NestJS가 기본으로 제공하는 검증 방식(DTO·ValidationPipe)과 에러 응답을 그대로 사용하지 못합니다. 검증은 shared의 함수를 직접 호출하고, NestJS가 내는 에러는 하나씩 찾아 같은 모양으로 바꿔야 했습니다.

거절 문구는 서버 응답에서 오므로, 문구를 고치면 서버를 다시 배포해야 화면에 반영됩니다. shared의 입력 검증 문구는 웹·앱 폼도 함께 쓰므로, 웹 재배포와 앱 새 빌드도 필요합니다.

그래도 이 방식을 선택했습니다. 웹·앱·서버가 같은 입력 규칙과 같은 검증 문구를 한 곳에서 가져오므로, 입력 규칙을 바꿀 때 세 곳을 따로 맞추다 어긋날 일이 없다고 판단했습니다.
